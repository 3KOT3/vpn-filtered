# vpn-filtered

Автоматически обновляемый список публичных VPN-конфигов, **через которые реально
работают YouTube и Telegram**.

Каждые 6 часов GitHub Actions скачивает исходную подписку, прогоняет каждый конфиг
через настоящий прокси-клиент и оставляет только те, где работают **и YouTube,
и Telegram**.

## Два списка: почему это важно

Здесь есть подвох, из-за которого «рабочие» конфиги могут не работать у вас.

**Раннеры GitHub Actions стоят за границей** (США/Европа). Прокси, который
прекрасно отвечает оттуда, может быть заблокирован РКН с вашего домашнего
интернета. Проверка «со стороны» этого не увидит в принципе: она честно отвечает
на вопрос «прокси рабочий и пропускает YouTube с Telegram», но не на вопрос
«доступен ли он из России».

Замер на реальных данных одного и того же `6.txt`:

| Откуда проверяли | Прошли YouTube | Прошли Telegram | Прошли по скорости | В списке |
| --- | ---: | ---: | ---: | ---: |
| Датацентр GitHub (США) | 88 | 79 | 50 | **50** |
| Домашняя сеть из РФ | 18 | 16 | 8 | **8** |

Разница ровно в этом: в v2rayNG из 50 конфигов отвечают те самые 8–10.

Поэтому есть **второй, локальный прогон**: он запускается на вашем компьютере,
проверяет конфиги из вашей сети и кладёт результат в `local.txt`. Именно эту
ссылку и нужно вставлять в v2rayNG / v2Box.

### Как обновить локальный список

```bat
local-run\check.bat
```

Двойной клик — скрипт скачает свежий `6.txt`, прогонит его через sing-box из
вашей сети и опубликует `local.txt`. Занимает меньше минуты. Настройки (токен,
порог скорости, путь к sing-box) — в `local-run/config.local.json`; этот файл
в `.gitignore` и в GitHub не попадает.

Запускать можно и по расписанию Windows — задача уже создана и обновляет список
каждые 2 часа:

```
Планировщик заданий -> vpn-filtered-local-check
```

Она запускает `local-run/refresh.bat` (тихая версия `check.bat`, пишет лог в
`local-run/last-run.log`). Запускается, когда вы вошли в систему. Удалить:
`schtasks /Delete /TN "vpn-filtered-local-check" /F`.

Бот рассылает уведомление только когда **список реально изменился** — сравнение
идёт по отпечатку конфигов, а не по времени прогона, поэтому каждые два часа
сообщений не будет.

## Откуда берутся конфиги

Источник — публичное зеркало
[`DarkRoyalty/shnajder-vpn-configs`](https://github.com/DarkRoyalty/shnajder-vpn-configs),
файл `githubmirror/6.txt` (около 130 строк, ~124 уникальных конфига: vless, trojan,
shadowsocks, vmess). Список файлов задаётся в
[`checker/config.json`](./checker/config.json) → `source.files`; чтобы добавить
ещё источники, достаточно дописать их номера в этот массив.

### Как часто обновляется зеркало

В workflow зеркала стоит `cron: "*/9 * * * *"`, то есть заявлено обновление каждые
9 минут. **Фактически GitHub запускает его намного реже:** по истории коммитов
интервал между обновлениями — от 2.5 до 9 часов (в среднем около 5 часов), все
запуски при этом успешные. Похоже, GitHub притормаживает слишком частые расписания.

Поэтому наша проверка раз в 6 часов идёт с запасом по свежести: каждый прогон заново
скачивает `6.txt` и никогда не переиспользует список от прошлого запуска.

### Расписание и минуты GitHub Actions

Сейчас стоит `cron: "0 */6 * * *"` — раз в 6 часов. Меняется одной строкой в
[`.github/workflows/check.yml`](./.github/workflows/check.yml).

Про минуты: лимит в 2000 минут в месяц относится к **приватным** репозиториям на
бесплатном плане. `3KOT3/vpn-filtered` — публичный, а для публичных репозиториев
минуты GitHub Actions не ограничены и не тарифицируются. Более того, на одном
маленьком `6.txt` прогон занимает около **1–2 минут**, то есть даже расписание раз
в 2 часа стоило бы примерно 400 минут в месяц — тоже в пределах 2000.

Так что 6 часов — это вопрос не экономии, а частоты обновления списка. Если захочется
посвежее, верните `0 */2 * * *`; на больших файлах зеркала (десятки тысяч конфигов)
прогон длится 20–30 минут, и вот там о частоте уже стоит думать.

## Как проходит проверка

```
строки в источниках
      │  разбор URI -> outbound-конфиг sing-box
      ▼
  уникальные конфиги ──► отброшено: 4 (неподдерживаемые транспорты vmess)
      │  TCP-коннект к серверу, 3 с
      ▼
  endpoint отвечает
      │  sing-box: GET https://www.youtube.com/generate_204   (ждём 204)
      ▼
  YouTube работает
      │  sing-box: GET https://core.telegram.org/             (ждём 200)
      ▼
  Telegram (HTTP) работает
      │  TCP-коннект до дата-центра Telegram (DC2 / DC1 / DC4)
      ▼
  Telegram (мессенджер) работает
      │  скачиваем 3 МБ с Google CDN, считаем Мбит/с
      ▼
  скорость ≥ 2 Мбит/с   ──►   1.txt
```

В список попадают **только** конфиги, прошедшие все шаги. Условия «или» нигде нет:
если через прокси открывается YouTube, но не Telegram, он в файл не попадёт.

Каждый шаг меряется по-настоящему: трафик идёт **через сам прокси**, а не просто
проверяется «сервер отвечает на ping».

### Это проверяется, а не подразумевается

В конце прогона чекер **жёстко сверяет** результат с главным требованием: каждый
конфиг в готовом списке обязан иметь подтверждение и по YouTube, и по Telegram.
Если найдётся хоть один без — прогон падает, список не публикуется, а в логе
появляется `ERROR: N конфигов в списке без подтверждённого YouTube или Telegram`.

Успешный прогон пишет в лог обратное:

```
пересечение подтверждено: все 50 конфигов прошли и YouTube, и Telegram
```

То же самое сохраняется в `status.json`, чтобы это можно было проверить без логов:

```json
"invariant": {
  "description": "в списке только те конфиги, где работают И YouTube, И Telegram",
  "kept": 50,
  "kept_without_youtube": 0,
  "kept_without_telegram": 0,
  "all_pass_both": true
}
```

Отдельно проверялось экспериментально: YouTube и Telegram прогонялись по всем
конфигам **независимо** (а не как в пайплайне — Telegram только по прошедшим
YouTube). Из 52 живых конфигов 1 работал только с YouTube и 0 — только с Telegram;
в готовый список не попал ни один из них.

### Про кэш ссылок

`raw.githubusercontent.com` кэширует файлы примерно на 5 минут и **игнорирует
параметр в ссылке**, поэтому `?t=...` кэш не сбрасывает. Для проверки раз в 6 часов
это неважно, но если открыть `1.txt` сразу после прогона, можно увидеть предыдущую
версию — надо подождать пару минут. Точный текущий `status.json` всегда виден через
GitHub API (`api.github.com/repos/3KOT3/vpn-filtered/contents/status.json`).

### Почему Telegram проверяется дважды

`core.telegram.org` отвечает 200 → значит, прокси видит инфраструктуру Telegram.
Но сам мессенджер работает по MTProto, у которого **другие IP — дата-центры**, и
Telegram блокирует часть хостинговых диапазонов. Поэтому дополнительно проверяется
TCP-коннект до дата-центров: у прокси с заблокированным IP он просто не откроется.

Настоящее TLS-рукопожатие тут использовать нельзя, и это проверено
экспериментально: на порту 443 у Telegram **fake-TLS**, то есть трафик только
маскируется под TLS. Реальный `ssl`-handshake сервер сбрасывает — все четыре DC
ответили `ConnectionReset`, тогда как TLS до `core.telegram.org` проходит
нормально. Поэтому проверка делается именно TCP-коннектом.

### Почему скорость меряется на Google CDN, а не на YouTube

YouTube не отдаёт большие файлы без авторизации и подписи запроса: пробовал
`youtubei/v1/player` с клиентами ANDROID, IOS, WEB, TVHTML5 — YouTube больше не
возвращает прямых ссылок на `googlevideo.com` без расшифровки `nsig`. Поэтому:

- **доступность YouTube** проверяется на самом YouTube (`generate_204`);
- **скорость туннеля** — скачиванием 3 МБ с `dl.google.com` (та же
  инфраструктура Google, стабильный публичный файл).

## Что не проверяется

- **Видимость из России.** Проверка идёт с раннеров GitHub Actions (США/Европа).
  Это отвечает на вопрос «прокси рабочий и пропускает YouTube с Telegram», но не
  отвечает на вопрос «не блокирует ли его РКН с вашего домашнего интернета».
  Конфиг может пройти проверку и всё равно не подключиться из РФ.
- **MTProto-доступность конкретных дата-центров Telegram.** Проверяется
  HTTP-доступность `core.telegram.org` — этого достаточно, чтобы считать, что
  Telegram через прокси не заблокирован.
- **Конфиги, которые sing-box не умеет.** Для выбранного источника это
  HTTP-обфускация vmess (3 шт.) и экзотический `headerType` (1 шт.). На больших
  файлах зеркала встречаются ещё `xhttp` (до 300 шт.), VLESS-шифрование
  `mlkem768x25519plus` (до 70), `obfs`-плагин Shadowsocks и битые строки с
  испорченным параметром `type`. Всё перечислено в `status.json` →
  `unsupported_reasons`.

Два случая отдельно, потому что они роняли **весь батч** (sing-box отказывался
стартовать, а не просто пропускал конфиг):

- `flow=xtls-rprx-vision-udp443` — вариант Xray, которого нет в sing-box.
  Приводится к обычному `xtls-rprx-vision`. Любое другое неизвестное значение
  `flow` отбрасывается, иначе sing-box падает с `unsupported flow`.
- Ключ Shadowsocks-2022 неверной длины (`2022-blake3-*` требует ровно 16 или 32
  байта в base64). Такие конфиги теперь отбраковываются заранее.

На случай нового неизвестного дефекта чекер всё равно делит упавший батч пополам,
пока не найдёт виновника, и продолжает работу.

## Запуск вручную

Actions → **Проверка VPN-конфигов** → **Run workflow**. Можно задать:

- `limit` — проверить только первые N конфигов (для быстрой проверки изменений);
- `min_mbps` — порог скорости;
- `min_keep` — не публиковать список, если выжило меньше N конфигов.

Локально:

```bash
# только разбор, без сети
python checker/check.py --parse-only --out-dir /tmp/out

# полная проверка на локальных файлах
python checker/check.py \
  --sources-dir ./sources \
  --sing-box /usr/local/bin/sing-box \
  --out-dir /tmp/out \
  --limit 500
```

Требуется только Python 3.9+ (никаких pip-зависимостей) и бинарник
[sing-box](https://github.com/SagerNet/sing-box/releases) (версия 1.14.x).

## Тесты

```bash
python -m unittest discover -s checker -p 'test_*.py' -v
```

43 теста на конвертер URI: реальные строки из зеркала, кодирование `&amp;`,
хвостовой слэш после порта, мусор в параметре `host`, поведение reality,
отбраковка `xhttp` / `mlkem` / `obfs` / legacy-vmess. Сеть не нужна.

## Если GitHub Actions не может закоммитить

**Settings** → **Actions** → **General** → **Workflow permissions** →
**Read and write permissions** → **Save**.

Без этого шага проверка пройдёт, но `git push` в конце упадёт с 403.
